# Jev decides qualification; Haiku only explains it

The gold-set spike (#103 / PR #104) scored TypeSafe Jev `jev-1.13.0` against the production DSPy path on `evals/datasets/qualifier_gold.jsonl` at the precommitted `noul >= 0.5` cutoff: 87.0% accuracy / 92.6% precision / 84.7% recall / **88.5% F1** / 310 ms, versus Haiku 4.5's 81.0% / 88.5% / 78.0% / 82.9% F1 / 1936 ms — and Jev rejected all 30 hard negatives outright. Jev is more accurate, over 6x faster, and cheaper on this specific yes/no decision, but it does not write text, so the qualifier still needs an LLM for the one-sentence `reasoning` that feeds the email draft and the CSV `qualifier_reasoning` column. Rather than run both models on every candidate, `qualify_lead()` now asks Jev first (`score_noul`, pinned to `jev-1.13.0` — not `jev-latest`, so scores don't drift under us) and only calls Haiku when the noul clears the cutoff: `is_qualified` and `score` are the noul verbatim, `reasoning` stays empty for rejected leads, and `icp_fit` is now always `{}` since Jev does not decompose ICP criteria (that decomposition is tracked separately as #99, not part of this change). The cost is a second vendor and API key (`TYPESAFE_API_KEY`) in the qualification path where before there was one, and a decision surface that TypeSafe's evals — not this repo's DSPy evals — now govern; `make eval-jev` remains the way to reproduce these numbers against the pinned model, and `make eval-dspy` still exercises `qualify_lead()` end-to-end but no longer benchmarks a qualification decision made by the model it names.

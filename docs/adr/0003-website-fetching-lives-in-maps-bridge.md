# Website fetching lives in maps_bridge, not a separate web bridge

Building a Site Profile means fetching an arbitrary URL that came from search results rather than calling one known API, so it carries a different risk profile than `search_places` — SSRF, unbounded response sizes, hostile timeouts. A separate `web_bridge` MCP service would express that separation in the deployment topology, but both bridges would be equally trusted by `ai_worker` anyway, so the isolation would be cosmetic while the cost (another container, Dockerfile, compose entry, CI job) is real for a single-operator tool. `fetch_site` therefore ships as a third tool in `maps_bridge`, keeping invariant #5 intact — one process talks to the network — with the risk handled in code: http/https only, private and link-local address ranges blocked, hard response-size and time limits. The trade-off is that the service name no longer describes its contents; renaming it to something broader is a separate, mechanical change.

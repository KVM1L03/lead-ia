# Read the client IP from the right of X-Forwarded-For

The per-IP request limiter (Layer 2 in `api_gateway/rate_limit.py`) keyed on the *first* `X-Forwarded-For` entry. That entry is whatever the client sent: a caller could rotate a fake `X-Forwarded-For: <random>` header on every request and get a fresh counter each time, bypassing the limit entirely. Cloud Run's front end *appends* the real peer address to the header rather than replacing it, so only entries added by our own trusted proxies can be believed — and those sit at the right-hand end. `client_ip_from_headers()` therefore takes the entry `TRUSTED_XFF_POSITION` places from the right (default `1`, the single Google front end on Cloud Run); `0` ignores the header and uses the socket peer, which is the right setting for local runs with no proxy. If the header has fewer entries than the configured position, we fall back to the socket peer rather than guess, so a misconfigured or absent proxy fails towards a shared bucket (stricter) instead of an attacker-chosen one. The cost is a deployment-coupled setting: putting an extra proxy or CDN in front of Cloud Run means bumping `TRUSTED_XFF_POSITION`, and forgetting to do so rate-limits all traffic behind that proxy as one client. This remains a soft demo guard; GCP budget caps are still the hard cost backstop (see `rate_limit.py` module docstring).

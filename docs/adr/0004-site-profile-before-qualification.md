# Site Profile is built before qualification, for every business found

The qualifier currently sees only `outreach_goal` and a serialized `PlaceDetails`, so a prompt like "dental practices with no online booking" — the example in the README — is judged against data that cannot answer it. Fetching the business website only for already-qualified leads would be cheaper (one fetch per qualified lead instead of per candidate) and was the obvious placement when the feature was framed as "find a contact address", but it leaves that blind spot open. Building the Site Profile before the qualify step instead means one fetch serves three consumers — qualification gets observable evidence for the user's criteria, the email draft gets personalization material, and the export gets a contact address — at the cost of fetching for candidates that will be rejected. That cost is HTTP and Haiku tokens, not metered API quota: Places calls are unchanged, and the fetch fan-out is parallel. Backfill rounds multiply it by the number of rounds.
